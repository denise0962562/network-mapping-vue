# 通知渠道管理

[返回文档中心](README.md)

进入「设置 → 通知渠道」（`/setting/notifications`）。邮件、飞书、Telegram 在同一页面以同级渠道展示，可任选一种或同时启用多种；各自选择事件，不互为主备。

## 配置与订阅

点击「添加通知渠道」，选择类型并填写配置：

| 类型 | 配置 | 凭据编辑 |
| --- | --- | --- |
| 邮件 | SMTPS 服务器、端口、发件邮箱、授权密钥、可选收件人 | 密钥留空保留 |
| 飞书 | 群机器人 Webhook、可选签名密钥 | Webhook/密钥留空保留，清除签名须勾选 |
| Telegram | Bot Token、Chat ID 或公开频道 @名称 | Token 留空保留 |

三个渠道均可选择健康告警、Scanner 掉线、Scanner 恢复、用户登录、周报生成、月报生成。选择「仅严重」只发送严重健康告警；其余事件为 warning。渠道类型创建后不能改，请新建对应类型。

邮件收件人可每行一个或用逗号分隔，最多 32 个。留空时登录通知发给用户本人，报告使用计划所选管理员，其余为当前启用的管理员。旧 SMTP 配置只导入一次，旧测试收件人不会变成真实收件人。

飞书关键词校验须允许 **Network Mapping**。Telegram 机器人须先加入目标群/频道并可发送消息，私聊须先发送 `/start`。服务端出口分别允许 `open.feishu.cn:443`、`api.telegram.org:443` 和 SMTP 服务器；Web 不需要公开机器人回调。

## 操作与状态

- 各渠道独立启停；可同时启用多个渠道接收同一事件。停用一个不会改变其他渠道。
- 「测试发送」须先保存并启用，同渠道至少间隔 30 秒。已入队不代表送达，以投递结果和实际收到消息为准。
- 修改/停用/删除取消旧配置下未完成的任务；已发请求不能撤回。再次启用只接收新事件。
- 投递历史支持渠道/状态筛选和游标翻页；浏览旧历史时暂停自动刷新。
- 离开页面取消读取请求并停止轮询，迟到响应不更新已卸载页面。
- failed 可手动重试，至少一次投递可能重复；查看事件 ID 排查。过期、取消、目标已变更的任务不会直接恢复。
- 维护期间每次领取前检查状态，允许在途完成；退出后处理待投递记录。
- 版本冲突 409 时刷新后重试。服务端和页面都只允许管理员管理。

报告生成时间、计划和默认邮件收件管理员在报告中心管理，通知方式在本页面管理；无需邮箱也能使用飞书或 Telegram 接收报告通知。报告中心显式发送/重发完整邮件、邮件模板测试继续使用首个邮件渠道的 SMTP 配置。

## 开发验证

```bash
node --test src/utils/notifications.test.js src/views/Notifications.test.js
pnpm build
```

页面测试覆盖三类渠道的请求字段、共享订阅、凭据保留及卸载清理。配套后端协议、升级和投递语义见后端 `docs/NOTIFICATIONS.md`。本地模拟 API 不代表真实邮件或群机器人联调成功。
